🔌 API Reference

Sign-in, conventions and every endpoint, for scripts and integrations.

Overview

What this is

Tracklab IM has one API: the same one the web app uses for everything it does. A script or another system can call it to read stock, raise documents or pull reports, as long as it signs in first.

  • It is not versioned. Endpoints can change between releases, so check the Release Notes after an upgrade.
  • This is not the same thing as the API Keys tab in Pricing. That tab holds the credentials Tracklab IM uses to call suppliers (DigiKey, Mouser, LCSC…), see Admin & Pro Tips.

Base address & format

  • Address: the address you open the app at, followed by /api. The examples on this page write it as https://YOUR-HOST/api.
  • Format: JSON in both directions. Send Content-Type: application/json with every request that has a body.
  • Size: a request body can be up to 20 MB. Attachments (scanned slips, POP / PO files, uploaded docs) travel as base64 inside the JSON.

Reading the endpoint tables

The tables further down list every endpoint by area. Five labels can appear next to a path:

  • Admin the signed-in account must have the admin role.
  • Changes inventory the account's role must be allowed to change inventory: admin, manager or engineer (not viewer).
  • Updates projects the account's role must be allowed to update projects: admin, manager or engineer (not viewer).
  • No session works without signing in (sign-in itself and password recovery).
  • Own token authenticates with its own token instead of a session.

Besides these labels, every call that changes something (POST, PUT, PATCH, DELETE) needs the account's role to allow changes in that area: stock and BOMs (admin, manager, engineer; deleting: admin, manager), bookkeeping and suppliers (admin, manager), projects and quality (admin, manager, engineer; deleting projects: admin, manager), automation (admin, manager). Otherwise it answers 403 with the reason, for example {"error":"Only admins and managers can change bookkeeping (customers, quotes, orders, invoices, bills, payments)."}. Reading is open to every signed-in account.

No label means any signed-in account can call it. A few internal maintenance endpoints are deliberately left out of the tables.

Signing in

Get a session

Post an email and password to /api/login. The response is the user plus a sessionId.

curl -s -X POST https://YOUR-HOST/api/login \
  -H "Content-Type: application/json" \
  -d '{"email":"integration@yourcompany.com","password":"..."}'

{
  "id": 12,
  "email": "integration@yourcompany.com",
  "firstName": "Stock",
  "lastName": "Sync",
  "role": "user",
  "status": "ACTIVE",
  "sessionId": "9f2c41d0...",
  "mustChangePassword": false
}

A wrong email or password, or an inactive account, returns 401.

Send the session on every call

Put the session id in the X-Session-Id header of every request.

curl -s https://YOUR-HOST/api/items \
  -H "X-Session-Id: 9f2c41d0..."

Without a valid session every endpoint except sign-in and password recovery answers 401 with {"error":"Sign in required"}.

Session rules

  • One session per account. Signing in again, from anywhere, ends that account's previous session.
  • 24 hours idle. A session that makes no calls for 24 hours expires. Sign in again to get a new one.
  • Check a session with POST /api/session/verify and {"sessionId":"..."}. It answers {"active":true}, or {"active":false,"reason":"..."} where the reason is idle_timeout or signed_in_elsewhere.
  • End a session with POST /api/session/logout and the same body.
💡 Tip: give each script its own user account. Because an account has one session at a time, a script that signs in as a person signs that person out of the app, and the person signing in again cuts the script off.

Admin-only endpoints

Endpoints labelled Admin answer 403 with {"error":"Admin access required"} to any other role. They cover user accounts, changes to the Documentation page's entries, supplier API credentials, deleting a kit, and the kit-booking BOM.

Endpoints labelled Changes inventory need a role that may change inventory: admin, manager or engineer. A viewer gets 403 with {"error":"Only admins, managers and engineers can change inventory, prices and part numbers."}. They cover starting and stopping bulk pricing runs, bulk pricing review decisions, and part-number fixes.

Endpoints labelled Updates projects need a role that may update projects: admin, manager or engineer. A viewer gets 403 with {"error":"Only admins, managers and engineers can change projects, project progress and production."}. They cover moving projects on the Project Progress board, holds and progress updates. Changing the list of stages is admin-only and answers other roles with {"error":"Only admins can change settings."}.

Limits on sign-in attempts

Too many attempts return 429 with a Retry-After header giving the wait in seconds.

CallLimit
Sign in20 per 5 minutes from one address, and 10 per 5 minutes for one address and email together
Forgot password20 per 30 minutes from one address, and 5 per 30 minutes for one email
Reset password20 per 30 minutes from one address
Session check200 per minute from one address

Calling from a web page on another site

This does not work, by design. A browser will not send the X-Session-Id header from a page served by a different site, so such a page can only reach the endpoints that need no session. Scripts and servers are not affected: call the API from your own back end, not from someone's browser.

Conventions

Errors & status codes

A failed call returns a JSON body with an error message. Validation failures add a details object naming the fields.

StatusMeaning
200 / 201Done. 201 is used when something was created.
400The request is malformed or a field is invalid.
401Not signed in, or the session has expired. On sign-in: wrong credentials.
403Signed in, but not allowed (an admin-only endpoint, or ending someone else's session).
404The record does not exist.
409The change is blocked by the record's state. Examples: deleting a sales order that has invoices, or replacing the lines of an order that is past DRAFT.
429Too many attempts. Wait for the number of seconds in Retry-After.
500 / 503Server or database problem. Safe to retry a read; check before retrying a write.

Field names

  • Bookkeeping, sales and purchasing use camelCase: clientId, orderNumber, unitPrice.
  • Inventory items are written with the stock table's own column names: serial_number (the stock code), name, stock, low_stock_lvl, man_pn_1, sup_pn_1 and so on. The stock code is also what goes in the path, for example /api/items/ANT-007.

Document numbers

Leave the number out when you create a document and the server assigns the next one in the form PREFIX-YEAR-NNNN, for example INV-2026-0007.

PrefixDocumentPrefixDocument
QUOQuotationPOPurchase order
SOSales orderBILLBill
INVInvoicePMTPayment made
RCPTPayment receivedEXPExpense
CNCredit noteLCLanded-cost batch
DNDelivery noteJEJournal entry
STMTBank statement

Updates change only what you send

Updating an item (PATCH or PUT) changes just the fields in the request. The same holds for PUT on customers, sales orders and their lines, sub-assemblies, fielded assets, parent/child part links, stock-ledger entries, alert subscriptions, auto-PO settings and automation rules.

On those PUT endpoints a field sent as null is ignored rather than cleared.

Amounts, tax & dates

  • Amounts are plain decimals with no currency symbol or thousands separator. Some responses return them as text ("1771.01"), so convert before doing arithmetic.
  • Tax on a line is set by taxRateId (an id from /api/tax-rates) and taxInclusive. A line's lineTotal includes its tax and taxAmount is the tax part, so the amount before tax is lineTotal − taxAmount.
  • Sales-order and quotation totals (subtotal, tax, total) are stored exactly as you send them. Calculate them from the lines before you post.
  • Dates go in as YYYY-MM-DD. Responses carry ISO 8601 timestamps.

Deleting & restoring items

Deleting an item hides it instead of removing it. Bring it back with POST /api/items/restore/:serial_number. Creating an item whose stock code belongs to a deleted item also restores it, with the new values.

Noticing changes made by others

GET /api/data-versions returns a counter per data area, as { "versions": { ... } }. A counter goes up whenever a write in that area succeeds. Poll it and re-read an area when its counter changes; the web app does this every 25 seconds.

Worked examples

Run a report

curl -s "https://YOUR-HOST/api/reports/profit-loss?from=2026-01-01&to=2026-03-31" \
  -H "X-Session-Id: 9f2c41d0..."

{
  "from": "2026-01-01",
  "to": "2026-03-31",
  "income":   [ { "accountId": 14, "code": "4000", "name": "Sales", "amount": 84210.50 } ],
  "expenses": [ { "accountId": 31, "code": "5000", "name": "Cost of Goods Sold", "amount": 51377.20 } ],
  "totalIncome": 84210.50,
  "totalExpenses": 51377.20,
  "netProfit": 32833.30
}

The figures above are illustrative. Only posted journal entries in the period are counted.

Create a quotation

One line, standard-rated at 15%, priced before tax. taxRateId is the id of the standard rate from /api/tax-rates.

curl -s -X POST https://YOUR-HOST/api/client-orders \
  -H "Content-Type: application/json" \
  -H "X-Session-Id: 9f2c41d0..." \
  -d '{
    "clientId": 30,
    "orderDate": "2026-10-01",
    "requiredDate": "2026-10-31",
    "status": "QUOTATION",
    "currency": "ZAR",
    "subtotal": 1000.00,
    "tax": 150.00,
    "total": 1150.00,
    "notes": "Example quotation",
    "items": [
      {
        "partNumber": "PSU-002",
        "description": "24VDC regulated power supply",
        "quantity": 1,
        "unitPrice": 1000.00,
        "taxRateId": 1,
        "taxInclusive": false,
        "taxAmount": 150.00,
        "lineTotal": 1150.00
      }
    ]
  }'

The response is the new order, with status 201 and its assigned number (QUO-2026-…). A quotation reserves no stock. To turn it into a sales order, call POST /api/client-orders/:id/accept.

GET/api/billsList bills.
GET/api/bills/:idGet one bill with its lines.
POST/api/billsCreate a bill.
POST/api/bills/:id/finalizeFinalise a bill: posts it to the ledger.
POST/api/bills/:id/voidVoid a bill.
GET/api/bills/:id/delete-impactPreview what deleting a bill would do, without doing it: reverseLedger, the payments that would be voided, stockKept, and blockers (reasons it cannot be deleted yet).
DELETE/api/bills/:idDelete a bill. Anyone may delete a DRAFT; any other status needs an admin (403 otherwise). Its ledger entry is reversed unless it was already void, and payments recorded against it alone are voided and returned as voidedPayments. Answers 409 with blockers, changing nothing, if a payment also pays other bills or is matched on a bank statement, or a landed-cost batch uses the bill.
POST/api/bills/:id/receiptAttach or replace the scanned slip / vendor invoice (a base64 image).
DELETE/api/bills/:id/receiptRemove the scanned slip.
POST/api/bookkeeping/ocr/receiptRead a receipt image into bill fields (OCR).
GET/api/payments-madeList payments made.
GET/api/payments-made/:idGet one payment with its allocations.
POST/api/payments-madeRecord a payment to a supplier.
POST/api/payments-made/:id/voidVoid a payment.
GET/api/expensesList expenses.
POST/api/expensesRecord an expense.
POST/api/expenses/:id/voidVoid an expense.
